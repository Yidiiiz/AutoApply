# Phase 5: deterministic answers and conservative candidate preflight

Scope is Phase 5 only. The existing uncommitted Phase 2–4 changes were inspected
and preserved. No live employer application, submission, private profile,
production database, or private history was used for validation. Production
`auto_submit` was not changed. Browser tests use disposable configurations and
local/intercepted fixtures, including the existing simulated submission tests.
AI/provider behavior was inspected from source and exercised with repository
mocks and synthetic fixtures. No external account connection, authentication,
or live service API call is part of this phase's validation.

## 1. Baseline

Read the Phase 1 audit and Phase 2–4 reports and inspected current source and Git
diff. Before production edits, the answer/core/dropdown/standing/disclosure/
experience/eligibility/freshness/fill-batch selection passed **253 tests in
56.35 seconds**. The preserved Phase 4 outcome file supplies the exact **725**
prior test IDs in `phase5-2026-09-25/baseline-ids.json`.

`phase5-2026-09-25/measure.py` constructs only temporary Config/profile/SQLite/
history storage. It considers twenty first-name fields, then twenty repetitions
of fifteen factual fields: names, contact details, education, authorization,
separate sponsorship periods, prior employment, conflict, SMS and privacy. All
mapper and resolver entry calls are included. AI is represented by the same
narrative admission predicate used by the engine and a counting stub; no live
provider is constructed. Separate regressions instrument actual provider entry.

The current Phase 4 first-name result reproduces the audit: **60 YAML reads and
60 SELECTs for twenty resolutions**. The representative workload performed
**1,120 YAML reads, 1,020 SELECTs, 40 writes and 40 events**. Those events were
standing disclosures considered by lookup, even though nothing was filled.
Both workloads already made zero AI calls.

## 2. ProfileSnapshot

`Config.profile_snapshot()` reads the canonical `data/private/profile.yaml`.
The file format and ordinary `Config.profile` interface remain compatible.
`ProfileSnapshot` recursively freezes the existing mapping/list structure;
it does not introduce another profile file or a competing set of fact paths.
It retains raw factual values, a normalized view, source path, and SHA-256
content revision. Known authorization/enrollment booleans are validated without
coercion; null remains null and false remains false. YAML dates retain their
ISO representation. Unicode normalization uses NFKC.

File mtime/ctime at nanosecond precision, size and file identity detect normal
edits/replacements without rereading YAML for every field. The explicit
`reload=True` boundary supports a forced reread. Equal contents have equal
revisions regardless of file formatting. Explicit `USER_PROVIDED` DB facts
overlay supported canonical paths in a new immutable view; original facts and
question references remain available. Boolean overrides recognize only Yes/No
or actual booleans. Missing/invalid boolean overrides do not become false.

The resolver reloads its lookup snapshot when canonical profile content,
verified-answer revision, or effective configuration changes. SQLite triggers
advance the answer revision for verified fact/memory changes; unrelated events
and memory usage timestamps do not advance it. `total_changes`, transaction
state and `PRAGMA data_version` detect local changes, rollback boundaries, and
other connections. No restart is required. Candidate decisions are evaluated
afresh and carry the effective profile revision.

## 3. FieldDescriptor and mapping

`concepts.py` is the registry for ordinary profile paths, aliases, categories,
answer types, scopes, factual fallback and special-policy markers. Identity
aliases still map `contact.first_name` to the existing `identity.first_name`
profile path. Legal/disclosure/standing grammars remain narrow dedicated rules;
they are not replaced by generic keyword-to-answer mappings. Dropdown lookup
and Controller verified-fact promotion use the registry too.

The immutable `FieldDescriptor` includes original/normalized question, semantic
key, mapping status, type, observed options, required flag, character/selection
limits, scope, employer/requisition context, effective policy, policy version,
and a deterministic signature. Resolution, memory compatibility, persistence,
standing/disclosure lookup and dropdown selection share that descriptor.

`UNKNOWN_FIELD` permits conservative deterministic label interpretation.
`REJECTED_FIELD` is a hard abstention against profile fallback and narrative
generation. It can resolve only through an exact compatible verified answer.
Phase 2's legacy exact free-text common-answer exception is retained; unsigned
option-bearing common answers cannot bypass a signature check.

Mapping caches include every classification signal, options, type, section,
required flag and policy version. Conflicting autocomplete/name evidence cannot
hit a label-only mapping. Semantic fallback remains optional, is not installed
in production, and is barred for unsupported factual/legal wording.

## 4. Exact answer precedence

1. `DO_NOT_ANSWER` blocks every source, including saved row replay.
2. Exact user-verified memory requires the current question signature, scope,
   compatible canonical profile revision when recorded, and no conflicting
   current verified override. `REQUIRE_USER` permits that compatible explicit
   user answer, but blocks the weaker sources below.
3. Complete standing eligibility assertions are considered for compatible
   boolean controls. Numeric GPA/date/essay values cannot be supplied by a
   boolean assertion. A rejected mapping cannot use standing assertions.
4. A rejected mapping can use only the exact compatible common-answer exception
   described above, then stops. Other fields continue through the complete
   service/survey and employer-aware disclosure grammars.
5. Explicit verified DB fact overrides, then observed school/city dropdown
   preferences, then canonical profile facts. The existing narrow U.S.-person
   export-status derivation remains separate. Authorization and sponsorship
   nulls are no longer filled from citizenship; unknown stays unresolved.
   Full name can be assembled only from both supplied names. Combined
   sponsorship requires both period-specific facts unless explicitly answered.
6. Explicit demographic, compensation, term-specific start-date, location and
   ordered technical-interest preferences; then scoped signed common answers.
   No preference is manufactured for absent values. Dropdown aliases must
   select exactly one observed option.
7. A saved application receipt can replay only with matching signature, policy,
   profile and verified-fact revision. Its structured provenance is restored.
8. Signed, verified writing-bank reuse with compatible question/requisition and
   profile revision, only for an admitted narrative prompt.
9. Existing grounded narrative generation and audit flow; generated proposals
   explicitly remain `verified=False`, including when confidence is 1.0.
10. Required fields and explicit user-input policy request input. Optional empty
    ordinary fields retain skip behavior. Existing optional-narrative failure
    holds and SmartRecruiters demographic restrictions remain intact.

`AnswerResolution` represents accepted versus rejected/input-required/optional
skip results. `Answer` carries source, verification, evidence, semantic key,
scope, signature, revision and provenance. Pure resolution performs no DB writes
or events. `record_answer_use` runs inside the accepted `save_answer` receipt
transaction, after successful browser input in Engine. Considering a standing
answer or memory match never increments usage. The SmartRecruiters completeness
pass supplies its result to filling, with revision/descriptor revalidation.

## 5. Provenance and persistence

Additive columns on `questions` retain semantic key, full question signature,
effective field policy, selection limits and answer provenance JSON. Existing
answer/source/confidence columns remain authoritative values; JSON does not
duplicate the answer text or the profile. Known answers retain full signatures,
semantic concept and provenance. Verified writing rows add signature and
profile revision. A small answer-revision table and narrow triggers support
invalidation. There is no history-schema or application-lifecycle rewrite.

Persisted evidence includes verification status, evidence IDs, source question
or memory/writing reference IDs, policy version, scope and profile/fact revision.
Standing-use event details survive replay. Existing history exports already
serialize question rows, so these fields round-trip into answer sidecars.
Unsigned old records remain readable; absent provenance is unknown, never
fabricated. Legacy label/type/options signature settings remain readable for
compatibility, but the new resolver requires the full signature column.

Signatures bind normalized question, semantic meaning, type, options (including
order), required/selection/character limits and policy. Sensitive/unknown
questions retain employer and requisition context even if a caller supplied
global scope. Office attendance and discovery-source confirmations never become global standing preferences. Ordinary global facts can be reused across applications. Changed
options, legal clauses, scope, mapping rejection, policy or user corrections
cannot silently reuse incompatible memory. Generated prose is not added to the
deterministic resolver cache or promoted to verified memory.

## 6. Candidate preflight

`candidate_policy.evaluate` is pure and data-only; `preflight` obtains protected
identity and verified-override evidence. Ordinary Engine, explicit controlled
Engine attempts, fill-only discovery and the fill-only runner use it. It runs
before `browser.new_page` in Engine.

| Decision | Meaning and evidence |
| --- | --- |
| ALLOW | Stored evidence contains no conclusive conflict; the existing positive eligibility assessment is complete; all later live guards still apply. |
| NEEDS_ENRICHMENT | Missing description/location/date, ambiguous or mixed geography, an unverified recognized legal requirement, or an incomplete role/eligibility assessment. Browser/listing enrichment remains permitted. |
| REJECT | Confirmed closed/removed; elapsed stale posting; explicit foreign-only country locations when international jobs are excluded; or a fully matched hard degree, graduation, authorization/citizenship or sponsorship clause contradicting a verified fact. |
| HOLD | Protected/retired application, exact protected duplicate, separately identified legacy identity ambiguity, wrong controlled target, or fill-only historical exclusion. |

Preflight never rejects from a title alone, absence of an internship word,
missing applicant facts, preferred qualifications, unknown qualifiers, degree
alternatives, or a graduation before/after clause whose interval was not proved. The existing eligibility function is consulted only to establish positive completeness; its broader negative heuristics produce NEEDS_ENRICHMENT, never a rejection.
Countryless cities, remote-only text and mixed locations remain unknown.
Conclusive requirement matching uses full clauses and preserves preferred
section context, including `Preferred Skills & Experience`.

Exact duplicate comparison retains canonical URL and current ATS tenant/
requisition identity. Distinct known requisitions with identical company/title
are distinct. Title similarity with incomplete legacy identity remains an
explicit `ambiguous_legacy_identity` review signal. Imported protected history
is still consulted. Controlled targets, permanent retirement and historical
fill-only exclusions are retained. The existing claim/start, URL-binding,
freshness, closure, upload and final-submission checks remain in place.

## 8. Tests

New regressions are in `tests/test_phase5_resolution.py` and
`tests/test_phase5_candidates.py`. They cover immutable/null snapshots,
revision/profile/preference invalidation, cross-connection corrections and
rollback, structured abstention, exact memory/standing/policy precedence,
disclosure scopes, signed privacy/SMS preferences, selection limits, generated
verification status, zero factual provider calls, conclusive/unknown candidate
evidence, exact versus legacy identity, browser avoidance, and mode protection.

Existing test IDs are retained. One standing test now asserts no event during
consideration and a correct event after accepted save. Three existing security
cases now prove both that distinct requisitions remain distinct and that a true
canonical URL alias still blocks. Their former title-only duplicate assumption
was the Phase 1 identity defect being corrected.

Validation results:

- Before production edits: **253 passed**, 56.35s.
- Initial resolver integration: **165 passed, 1 failed**, 41.47s; the one failure
  was the old lookup-time standing-event assertion, updated to test explicit use.
- Broader implementation integration: **213 passed**, 175.77s.
- First new regressions: **78 passed, 1 failed**, 25.84s; the failure exposed and
  fixed preferred-section parsing, without relaxing the test.
- Unit/persistence/answer follow-up: **262 passed**, 63.93s.
- Safety/history/freshness/maintenance/controlled/persistence plus new tests:
  **374 passed**, 266.40s.
- Latest answers/new tests/SmartRecruiters/narratives: **140 passed**, 161.87s.
- Final scope/positive-enrichment checks plus core/fill-only: **138 passed**, 83.35s.
- The first complete run exposed a draft-preview compatibility issue: a draft
  request without a persisted application ID tried to construct reusable
  requisition scope. Such previews now bypass reuse and continue the existing
  draft flow; the original missing-facts regression passes (**1 passed**, 0.92s).
- The next complete run had **814 passed, 1 failed**, 762.93s. The remaining
  failure was a 3-second timeout in the unchanged security fixture's local
  `page.set_content` setup. An unchanged rerun, together with provider and
  integration checks under the offline guard, passed **17 tests**, 10.35s.

- Exact Phase 4 ID comparison: **725/725 passed**, zero missing or nonpassing;

The final run uses `offline_validation.py`, a test-only pytest plugin. It
rejects external Python socket connections and DNS lookups, adds Chromium
background-networking/DNS restrictions, and installs a loopback-only browser
route. Existing test-specific mocked routes take precedence so synthetic
employer URLs can still be fulfilled locally. Production browser configuration
is unchanged. The full browser suite runs sequentially.
