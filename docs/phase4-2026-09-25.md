## 2. Persistence changes

| Change | Old behavior | New behavior and durability |
| --- | --- | --- |
| Explicit DB batches | Each upload event, answer receipt, or hold event could export separately. | Existing `Database.transaction()` groups immediately related DB-only writes. One commit precedes one dirty export. No new transaction spans a browser/provider/network await. |
| Flush entry | Every DML invoked `flush_history`, even inside a transaction; clean writes opened an empty export transaction. | DML inside a transaction waits for its commit boundary. Clean dirty-queue checks avoid empty export transactions. Unchanged explicit batches avoid flush calls. The dirty queue is re-read after acquiring the DB write lock. |
| Security observations | `diagnostics_at`/`updated_at` changed on every inspection. | Under the existing write transaction, compare supplied state/evidence fields. Identical observations issue no UPDATE, mark nothing dirty, and do no export. Meaningful field changes still commit/export immediately. Confirmation-erasure checks run before suppression. |
| Archive lookup | `archive_application` forced an export even after a successful commit export. | Flush pending dirty work, refresh the history path cache, and return the folder. Missing application bundles still force repair. Ordinary mutations retain their normal synchronous boundary. |
| Draft history | Draft settings only reached a sidecar through a later event/forced archive. | Narrow SQLite triggers on `draft:<question_id>` setting insert/update/delete enqueue the owning application transactionally. Controller draft + supporting event now share one DB batch after the provider await. |
| Probe callbacks | Each observation event exported bundles/statistics; each settings write also opened an empty export transaction. | Events and paired settings remain immediately committed in short transactions with `sync_history=False`. Events retain durable dirty entries. Prepare/finish, ordinary critical mutations, archive lookup, graceful close, and restart provide export boundaries. No worker, timer, or background queue was added. |
| Description file | Always rewritten, without atomic replacement. | Uses the shared UTF-8 compare/fsync/atomic-replace helper. Changed description bytes are durable; unchanged files retain bytes and mtime. |
| Statistics file | Fresh `generated_at` forced replacement on every sync. | Calculate once per sync; if every substantive result is equal, retain `generated_at` and the existing file. Day/week/month changes and changed listing metrics still replace it. |

`diagnostics_at` on a repeated multi-field security observation now means the
last changed observation, rather than a polling heartbeat. Explicit
timestamp-only diagnostic captures still persist. Changed HTTP status, message,
URL, provider, challenge, verification, manual hold, screenshot reference, and
confirmation evidence remain meaningful fields. Evidence events are not dropped.

`statistics.generated_at` now identifies the last changed aggregate artifact,
not the most recent export attempt. Calculations still run at a real dirty sync;
this phase does not add incremental analytics or suppress time-dependent results.

## 3. Transaction boundaries

The single batching API remains `Database.transaction()`. Its optional
`sync_history=False` affects only the export boundary, never the DB commit.
Production use of that option is confined to SubmissionProbe observation
`record` and paired `save` writes. It is not used for critical state transitions.

Immediately committed/exported batches include:

- A saved form answer and its `LIVE_CONTROL_COMMITTED`/SmartRecruiters
  `FIELD_FILLED` evidence, after `adapter.answer_question` completes.
- Upload lifecycle events, upload-result setting, and `UPLOAD_READINESS`, after
  the browser readiness await completes. In-memory events clear only after the
  persistence boundary succeeds.
- An Engine hold transition and its supporting hold event.
- READY plus the `READY_FOR_MANUAL_SUBMIT` state/evidence, before retaining the
  manual page and returning.
- A Controller-generated draft and its supporting event, after generation.
- Existing adapter progress transactions and existing user-answer transactions.

The submission-intent transaction remains at its original location before
`probe.intent()` and before `await probe.physical_click()`. Export failure at
that boundary leaves the intent committed and prevents the final interaction.
Affirmative confirmation still calls the ordinary immediate `transition` path;
its committed final state survives export failure. Manual/security holds,
ambiguous-submission protection, controlled holds, retirement/deduplication,
and user answers retain their immediate commit boundaries.

Probe events commit individually; two related probe setting rows commit
together. They may accumulate in the durable dirty queue during observation.
The confirmation timeout, sampling, security checks, physical-click guard, and
no-retry rule are unchanged. This is synchronous explicit-boundary export,
not asynchronous background exporting.

Removed forced synchronization was audited as follows:

| Site | Dirty source and replacement boundary | Failure / exit behavior |
| --- | --- | --- |
| `Controller.answer` final archive call | Question/application/events triggers; existing enclosing transaction commits then flushes. | Pre-commit failure rolls back all evidence; export failure preserves committed rows and pending dirty work; startup retries. |
| Engine discovery pre-update archive call | The following application `stage='discovery'` UPDATE marks dirty and exports synchronously. Earlier discovery mutations already committed. | Stage/export failure cannot erase earlier discovery or protection evidence; committed stage changes remain recoverable. |
| `archive_application` forced-ID enqueue | Normal application/question/job/source/event triggers, plus newly tracked draft settings. Pending work is flushed; missing bundles explicitly enqueue repair. | Export failure propagates without acknowledging dirty work. Close retries; abrupt exit leaves SQLite dirty work for startup. |

## 4. History synchronization

SQLite `history_dirty` remains the durable work queue. Application mutations and
their dirty triggers commit together. `flush_history` still obtains
`BEGIN IMMEDIATE`, reads the pending IDs, synchronizes all pending bundles and
statistics, then deletes/commits the dirty entries. If any file replacement,
directory rename, or statistics write fails, that acknowledgement transaction
rolls back. The original mutation commit remains authoritative.

The lock order is **DB write transaction -> history thread/process lock**.
`ApplicationHistory.sync` rejects calls not owned by `Database.flush_history`.
History lock ownership is tracked per thread/root; Database entrypoints reject
attempting DB access without an existing DB transaction while holding that
history lock. A separate SQLite connection cannot write during an export; its
subsequent committed event has its own dirty entry and is exported separately.

Revisioned snapshot/ack export is **deferred**, as permitted by Task 9. Export
currently also repairs screenshot paths in SQLite after moving state folders,
merges imported metadata/assets, and participates in listing-statistics and
migration locking. Simply releasing the write lock would make the dirty-row
acknowledgement unsafe. Phase 4 reduces how often that path runs while retaining
the existing proven serialization. In particular, the legacy export/ack
transaction still spans filesystem work; this is a retained limitation, not a
claim that all filesystem work has moved outside SQLite transactions. No new
mutation transaction adds filesystem work, browser awaits, or provider calls.

`.cache-token.json` is a small reader-invalidation token, **not** a DB export
revision or acknowledgement protocol. Statistics can now remain unchanged while
application records change. Under the history lock, publish a fresh token before
export/validation writes; cached readers rescan after the lock becomes available.
Publishing before writes also invalidates readers after a partial failed export.
Only a successful DB dirty-queue acknowledgement marks work clean. Tests cover
unchanged aggregates with changed application evidence and separate readers.

On graceful `Database.close`, pending observations are flushed; the connection
closes even if export fails, leaving committed dirty work for restart. Abrupt
termination requires no graceful callback: startup validation and the durable
dirty queue rebuild pending bundles. Closing twice remains harmless.

Imported unknown fields are still merged from the prior canonical record.
Existing status-history union, source provenance, question/answer sidecars,
confirmation fields, intent, retirement settings, reconciliation events, and
attachment preservation behavior are retained. No simplified record schema is
introduced. Existing protected-submission byte-preservation tests still apply.

## 6. Crash-safety validation

New deterministic tests exercise:

- Failure before mutation commit: application state, events, and dirty entries
  roll back, with no history synchronization.
- Intent and confirmation commit followed by export failure: a separate SQLite
  connection sees the committed evidence and dirty row. Simulated abrupt close
  plus a new Database instance exports it; recovery retains unknown-intent holds
  and monotonic confirmation.
- Failure during atomic replacement of `events.json`, `job_description.txt`,
  or `statistics.json`: previous bytes remain intact, temporary files are
  removed, dirty work remains, and retry completes.
- DB-before-history lock enforcement and a second connection's write attempt
  during export. The later committed mutation cannot be cleared by the earlier
  export. A new revision-N/N+1 protocol test is not applicable because that
  protocol was deliberately not introduced.
- Probe callbacks with durable events/settings and zero exports, abrupt restart,
  and graceful close. Callback evidence is not merely held in memory.
- A local Engine fixture checks intent from a separate connection immediately
  before the one physical submission interaction. Injecting intent-export
  failure results in zero click calls and zero local submission requests.
- Unknown imported nested metadata, attachment bytes, and reconciliation events
  surviving optimized exports and a final-state move.

The existing Windows rename retry, interrupted move/deletion, malformed-byte
preservation, imported-submission duplicate protection, controlled execution,
retirement, and confirmation-before-screenshot-error regressions are retained.
