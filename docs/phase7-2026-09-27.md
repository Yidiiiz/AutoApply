## 2. Lifecycle model

`autoapply/lifecycle.py` owns application transitions and dimension writes. `Database.transition`, `claim`, `recover`, `retry`, `fail`, and `update_security` are compatibility facades. Runtime Engine, Controller and handoff operations use this service. SQL storage, question persistence, ingestion, listing maintenance and archive repair retain their existing responsibilities.

Canonical operations include claim, begin_attempt, transition, metadata, dimensions, delivery, record_hold, record_ready, record_submission_intent, record_confirmation, record_failure, resolve_input, resume, release_hold, begin_reconstruction, restore_checkpoint, retry, recover and reconcile. Status, job projection, relevant dimensions, timestamps and event evidence commit together. No transaction spans browser I/O. Unchanged observations still avoid writes and exports.

The explicit transition table covers QUEUED → CHECKING → APPLYING; APPLYING → NEEDS_INPUT or READY; READY → SUBMITTING; SUBMITTING → SUBMITTED or a manual/unknown hold; FAILED → RETRY; and RETRY → CHECKING. Holds and terminal outcomes can stop unfinished work. The legacy transition facade accepts older transition sequences while retaining confirmation, intent, final-state, retirement and fill-only protections. It is not the entry point for new orchestration.

Final states cannot be reopened by ordinary transitions, including listing cleanup. A retirement guard independently prevents claims, retries and resumption. Existing submission intent prevents runnable states until evidence-backed reconciliation. SUBMITTED requires affirmative evidence. A confirmed projection cannot be erased by a later verification result.

Compatibility projections remain: QUEUED/RETRY → DISCOVERED, CHECKING → OPENED, APPLYING → FILLING, READY → READY_TO_SUBMIT, and input/auth/manual holds → MANUAL_REQUIRED. An uncertain interaction projects UNKNOWN. A validated open fill-only page can project READY_FOR_MANUAL_SUBMIT; page release downgrades that projection. SQL status and job status remain compatible with archive/history readers. Security, verification and listing values remain separate.

The migration is additive: `attempt_started`, `max_retries`, `delivery_state` and the `manual_commands` ledger. Existing three-column `manual_requests` and history formats remain readable. Older active rows with already-counted attempts are conservatively marked started during migration. Explicit incident repair and archive screenshot-path repair remain identifiable exceptions to ordinary lifecycle orchestration.

`autoapply/status.py` provides the snapshot used by status, inspect/explain and batch reporting: lifecycle, listing, security, verification, hold, retry/budget/delivery, intent, confirmation, actual live-page availability and checkpoint readiness. A persisted flag alone never proves a live browser.

## 3. Failure and retry model

`Failure` carries category, reason, operation, stage, delivery and retryable. It preserves existing network/site/rate, input, upload, authentication, validation, security and execution-approval categories, adding PROCESS_INTERRUPTED and STEP_TRANSITION_UNKNOWN. Practical exception classification now uses actual Playwright timeout and cursor-instability types.

Delivery distinguishes NOT_STARTED, POSSIBLY_DELIVERED and OBSERVED. A durable Next intent is possibly delivered; observed advancement clears that uncertainty for subsequent work. Final submission intent is durable before the physical click. A crash or network failure with possible delivery produces an UNKNOWN hold, with no automatic repeat interaction. Durable final intent takes precedence over all retryable categories. Persisted delivery uncertainty also overrides an otherwise generic typed failure, and unknown outcomes clear any resume permission inherited from an earlier manual step.

`RetryPolicy` is the sole application retry decision policy, invoked by lifecycle operations. Each failed attempt gets one decision and a durable event containing the typed failure, decision and budget. Manual, security and controlled holds veto retry; final and retired applications remain excluded. RATE_LIMITED is now a security hold, so it cannot retain an automatic retry schedule. Primitive observation/deadline behavior from Phase 6 is unchanged.

A claim reserves work and does not increment attempts. `begin_attempt` increments once immediately before browser work and stores the configured retry budget. With max_retries=N, at most N+1 attempts can begin. Recovery returns an untouched CHECKING reservation without consuming an attempt; acted work is evaluated against the persisted budget. Repeated startup alone costs nothing, while repeated crashes after starting browser work exhaust the budget. A same-page manual continuation does not create a fresh attempt. Explicit reconstruction starts and counts a new navigation attempt. Resolving input, restoring a checkpoint or reconciling not-submitted cannot grant an exhausted budget another attempt.

## 4. Manual command model

`ManualCommand` contains action, application_id, session_token, parameters and an idempotency ID. Both Controller.command (CLI) and Controller.route (Discord) parse the same representation once. Resume, resume-manual, inspect-manual and verification enqueue JSON envelopes; new bare commands are not produced. Legacy bare inspect is understood only as an ordinary reconstruction request, subject to current guards.

The durable sequence is PENDING → IN_PROGRESS → ACKNOWLEDGED or FAILED. Claiming first persists the command ledger and acknowledgement in the same transaction that removes the compatibility queue row. Restart marks interrupted IN_PROGRESS commands FAILED with an inspection-required result; it never blindly replays them. Duplicate IDs cannot execute again. Stop durably cancels pending commands. Malformed legacy payloads are recorded as failed instead of disappearing or looping indefinitely.

Controlled inspection/resume requires the configured application and the correct explicit token. The worker also compares the token to its in-memory live-session owner. Token validation precedes resolution of pending facts. Stale/missing sessions cannot imply same-session continuity. Ordinary input reconstruction remains explicit and budgeted; controlled sessions cannot silently reconstruct, clear their configured target, or remove an execution-approval hold. Saving exact applicant answers remains distinct from authorizing continuation.

Parity tests cover resume, resume-manual, inspect-manual, inspect, stop, answer, skip and reconciliation, plus correct/wrong/missing controlled tokens, stale commands, duplicates and crashes after claim. The CLI retains JSON formatting for direct inspect; the underlying snapshot and target guard are shared.

## 5. Reconciliation

Both interfaces use `Lifecycle.reconcile`. An uncertain submission and nonempty employer evidence are required. Submitted reconciliation records confirmation and preserves independent verification state. Not-submitted reconciliation may clear the current uncertain intent only after appending an audit event containing its prior timestamp, user outcome, evidence and evidence source. It respects security, controlled, retirement and attempt-budget guards. Clearing the current field never erases the historical intent or its events.

`autoapply/conflicts.py` supplies one policy for preflight and submission: canonical URL or ATS identity, including tenant and requisition/opportunity ID. Distinct known requisitions with the same title remain distinct. Incomplete legacy identities can return `ambiguous_legacy_identity`, rather than an exact match. Imported protected history uses the same identity policy as SQLite rows. No title similarity is treated as exact identity, and no unmeasured indexing claim is made.

## 6. Fill-only readiness

The persisted/read-only terms are:

| Readiness | Evidence |
| --- | --- |
| FILLED_CHECKPOINT | Progress saved; preparation may be blocked or incomplete |
| RECONSTRUCTABLE_CHECKPOINT | Validated preparation and saved answers/checkpoint; replay has not been verified |
| RECONSTRUCTION_VERIFIED | An explicitly requested fresh navigation and replay passed validation and resume-hash checks |
| LIVE_READY_FOR_MANUAL_SUBMIT | A currently open owned page has validated ready state |

Default successful preparation saves a checkpoint and releases the sole application page through its Phase 6 lease. It does not replay the application. `BatchPolicy(verify_reconstruction=True)` / `--verify-reconstruction` requests the stronger replay explicitly. Reconstruction failure never sets verified readiness. Closing a page removes its live-ready projection and session claim. Historical successful reconstruction is evidence of that check, not a promise that a future ATS session will still reconstruct.

The specialized runner defaults to `target_count=5`; the reusable policy accepts other positive targets. Its first processed application is the smoke test. Only successful preparation/checkpoint completion passes the smoke gate. Failure stops continuation; exhaustion is reported separately. Report fields distinguish prepared count, verified reconstruction count and live-ready count. A completed sequential checkpoint batch has zero live-ready pages after release.

The whole-run invariant accumulates final-button observations, recognized completed submission requests, blocked final requests and new submission intents. The engine forbids final intent in fill-only mode before reaching the physical Submit operation; the probe guard is additional defense. Browser context instrumentation observes actual final-button clicks and recognized request completions. The route aborts recognized final endpoints/actions and latches the violation. New intent detection uses both current fields and durable SUBMITTING events. Checks occur at application boundaries and interruption points; any violation stops further processing. Counters never reset per application.

Request recognition uses the existing submit/finalize endpoint and action rules, and the click observer uses semantic final-button labels. These are defense-in-depth signals, not a universal classifier for arbitrary employer APIs. The primary protection is that fill-only engine policy never enters submission. Tests independently check local page click counters, intercepted POSTs and stored intents, and deliberately exercise observer violations using synthetic pages only.

The central one-application-tab limit remains one. Reports expose current leased pages, maximum observed pages and unexpected popup violations. Startup blank pages are removed before enforcing a newly enabled fill-only policy. Unexpected popups remain latched violations and are closed through ownership machinery. Explicit verification reuses the sole owned page; it does not open another tab.

## 7. Incident separation

Normal resume no longer reloads modules, swaps object classes or responds to the old upload refresh setting. `autoapply/maintenance.py:refresh_untouched_upload_protocol` is an explicit maintenance operation: it requires an untouched tracker and no submission intent, preserves evidence, acknowledges the old request and records that code updates require worker restart. Two existing repair tests retain their IDs and now invoke this explicit entry point.

The existing 5310 incident-only reload script stays explicit and now passes its owned live-session token to resume. The 5310 eligibility repair, forensic scripts, historical exclusion IDs, destination approval records and special requirement for exactly five HTTPS approved destinations remain operational safeguards. They were not deleted or moved through a broad repository restructure. The fill-only runner retains them alongside the general lifecycle policy. Restoration uses budgeted lifecycle permission instead of setting retry_allowed merely to unstick work.
