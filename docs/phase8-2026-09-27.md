The baseline commit and preservation hashes are in [integrity.json](phase8-2026-09-27/integrity.json). No subsequent optimization phase is started.

No live employer form, provider, Gmail, Discord, account login or submission is used. Production/private configuration and history are untouched; `auto_submit` is not enabled. Existing disposable regression fixtures still simulate submission to test its safeguards.

## 3. Narrative request/signature model

`narratives.NarrativeRequest` is frozen and contains the normalized question, existing **Phase 5 field signature**, narrative category, employer/requisition, role title, character/word limits, effective ProfileSnapshot revision, verified-answer revision, verified-writing revision, narrative policy version, provider-policy fingerprint and relevant-context fingerprint. Stable JSON hashing supplies the narrative signature. No timestamps, control IDs, browser generations, application status or telemetry events are included.

The existing field signature remains authoritative for type, exact semantics/options, scope, policy and requisition identity. A new narrative signature is additional compatibility evidence, not a replacement. Role, description where relevant, source facts, style samples, writing policy and provider/model configuration are bound separately. Cosmetic control replacement can reuse a proposal. Material wording, field limits, employer, requisition, profile facts, graduation, projects/experience, fact corrections, writing-bank changes, samples or policy/config changes cannot reuse an incompatible proposal.

The manager uses the same resolver as Engine, including explicit user-provided DB fact overrides. It rechecks revisions and request inputs after provider awaits before publishing a result. Full profile and verified-writing revisions deliberately invalidate conservatively; unrelated application events and writing usage timestamps do not invalidate the narrative signature. Filesystem metadata and DB revision checks still occur; they are not described as free work.

Generated saved receipts now defer to the narrative service instead of using the weaker factual receipt replay check. Thus an already-filled question cannot bypass listing/policy/provider-context invalidation. Browser generation and commitment remain separate boundaries.

Default generated scope is the Phase 5 requisition scope. Explicit employer scope can share within the same canonical requisition even when a caller's local application/control ID differs. **It does not widen Phase 5's signature to share generated motivation across different requisitions.** Existing globally reusable verified common answers remain the resolver's responsibility. Employer-only cross-requisition generated sharing is deliberately not offered.

## 4. Cache and provenance

Three distinct sources remain:

| Source | Meaning | Verification |
| --- | --- | --- |
| `GENERATED_PROPOSAL` | Audited provider output, or an explicit factual-summary template | `verified=False` until existing explicit acceptance |
| `VERIFIED_WRITING_MEMORY` | User-confirmed signed writing, compatible under Phase 5 | `verified=True` |
| Verified applicant facts | Canonical user-entered profile and supported explicit user-provided fact overrides | Existing Phase 5 authority; prose cannot populate them automatically |

The additive `narrative_cache` table maps signature to a `written_responses` proposal ID and provenance. Answer text is stored once in the existing writing table, with `verified=0`. Cache metadata includes signature, answer hash, provider/model, source-context and profile/fact/writing revisions, policy version and source IDs/quote hashes. Full proposal provenance is also retained on the historical writing row, so cache eviction cannot erase its signature/model/evidence metadata. It does not store another complete profile, listing, or factual-source set. Exact quotes are checked at generation; stored hashes bind that evidence without duplicating source blocks. This is provenance, not a proof that a model's entailment judgment is correct.

The cache has a fixed **256-entry insertion-order bound**, pruned in the same short transaction as a successful insertion. There is no hit-time LRU write, timer, external cache or background process. Eviction removes cache eligibility, not the existing proposal/audit records; historical writing retention remains the existing policy. Bounded per-manager prepared-context and verified-writing lookup maps also have 256-entry limits.

Lookups perform no writes, no usage increments and no events. A new proposal writes one writing row, one cache row and executes bounded pruning in a DB-only transaction after provider work. `record_answer_use` records grounding provenance only in the existing accepted-receipt transaction after successful browser input. Failed/rerendered controls can retrieve the same proposal without another provider call.

Verified-writing triggers advance a separate revision for insert/delete/content/signature/verification edits, excluding last-used timestamps. Cross-connection changes and rollback are tested. Generated inserts do not invalidate their own cache. A partial verified-writing index supports the measured exact lookup. Existing Phase 3 indexes and Phase 4 durability boundaries are unchanged.

User corrections are resolved before the generated cache. Controller retains the replaced proposal's provenance in the accepted answer, while the original generated row and prior events remain intact. Explicit draft previews retain separate draft provenance. Repeated generation/use does not increase verification or promote prose into factual memory.

## 5. Provider lifecycle and failures

AIManager owns provider objects for one session, keyed by configuration fingerprint. Config changes clear clients, selection decisions and prepared contexts. Configuration order, tier, preferred model and billing requirements are preserved; no new provider or API is configured. A failed provider is removed from the pool so later work reinitializes it.

CLI subscription readiness is reused for at most **60 monotonic seconds**. Configuration/model and credential-file metadata changes invalidate it; a declared credential/config revision in provider settings also changes the fingerprint. Failed status checks are not cached. Any generation failure or cancellation expires readiness. Credentials stored outside the watched file are still covered by the finite expiry and failure revalidation; no remote health result is trusted indefinitely. The implementation reads only credential metadata for invalidation, not credential contents.

Browser-provider security, usage and model observations remain fresh on each page/poll. Client/config validation is reused, but page health is not cached across pages. Existing browser ownership and one-tab fill-only rules are unchanged. CLI transport optimization does not introduce another application browser, persistent provider conversation, concurrent request or service.

`ProviderUnavailable.category` distinguishes UNAVAILABLE, AUTHENTICATION, RATE_LIMIT, TRANSPORT_TIMEOUT, MALFORMED_RESPONSE, EMPTY_RESPONSE and CONTENT_VALIDATION. Conservative configured-provider fallback remains. No failure path produces replacement factual information. Existing optional-narrative failures still hold for input, as explicitly covered by the retained browser regression.

## 6. Context, templates and output validation

One context builder selects relevant user-entered factual categories: education, skills, projects, employment/experience/leadership, career interests or location context. Category-named verified blocks are selected conservatively; arbitrary unclassified blocks are not inferred into relevance. Sensitive/legal block identifiers are excluded. The profile's identity/contact/citizenship/authorization sections are not sent wholesale. Location interest with no supporting location/interest facts requests input rather than inventing motivation.

Company/role metadata and listing description appear once in `job_context`; duplicate top-level copies are removed. Project-only writing omits unrelated listing description and education. Shared safety instructions remain in provider wrappers; the central writing policy describes tone and factual restrictions. Style samples are explicitly not factual sources, are read at most once per metadata revision, and are part of the compatibility signature.

Exact prompts “Describe your education/skills/project names/availability/links” use deterministic labeled/list summaries of existing facts before provider selection. Missing data or exceeded limits hold for input; no template invents enthusiasm, employer affinity, dates or qualifications. The summaries remain unconfirmed writing proposals even though their component facts are verified.

Deterministic output checks require nonempty text, ordinary text-field compatibility, exact character/word limits, no obvious placeholder/style violations, and no numeric claims absent from supplied verified facts. A recognizable graduation-year statement must agree with the current snapshot. Structured fact IDs and the existing exact-quote grounding audit remain mandatory for provider prose. These checks do not claim to prove arbitrary natural-language entailment; no new AI judge loop or quality score is introduced.
