## 2. Changes

### One maintenance policy

Previously scan cleaned before and after source polling, ordinary claim cleaned
again, and status/pending/queue cleaned during display. `ListingStore.maintain_listings`
now owns one durable policy shared by startup, scan, and ordinary claim:

- A five-minute periodic deadline bounds ordinary reporting maintenance.
- Indexed per-listing deadlines trigger sooner at expiry or changed evidence.
- Age-window changes invalidate maintenance and reevaluate all listing evidence
  once; unchanged configuration is no longer rewritten on every ingest.
- Controlled execution skips ordinary global maintenance without changing its
  target. Explicit claim still guards only its requested application.
- The scan completion boundary only refreshes dirty listing statistics. No
  transaction spans source/browser awaits.

A restart reads the same persisted schedule. Initial upgrade seeds existing
identities once. First listing migration and age-window changes deliberately
perform a full evaluation, preserving the legacy migration report and backup.
Explicit `cleanup_stale_listings` runs a maintenance cycle, while ordinary callers
use the due gate. A due cycle with no changed evidence writes only two schedule
settings; an idle not-due call does no SQL writes or cleanup.

### Candidates and changed-only writes

The previous implementation read every job, read the age-window setting and
observation per row, then unconditionally updated each observation. A small
`listing_maintenance(identity_key, due_at)` table now holds derived work:

- New or edited posting/closure/identity evidence is queued transactionally by
  SQLite triggers, including edits from another connection.
- Fresh listings have an expiry deadline. Closed/removed fresh sightings still
  age into culling. Future legacy dates have a reevaluation deadline.
- Stale rows and unknown dates without posting evidence have no timed work.
  New source evidence can queue them again; discovery never supplies posting time.
- An inclusive 30-day cutoff expires at posting time plus the validated window
  plus one microsecond. The deadline only selects candidates; `freshness.py`
  remains the authority for the actual decision. Dates use existing UTC helpers.
- Candidate jobs, observations and queued-application metadata are joined in a
  bounded query. Missing last-seen provenance uses an indexed source lookup in
  that query. The window and reference instant are captured once for the batch.
- Job fields and observation state are compared before writing. Cleanup does not
  modify source sightings, duplicate counters, or discovery-age evidence.

Work acknowledgements and listing mutations commit together. A failed batch
leaves its work pending. Mutation triggers from cleanup itself are acknowledged
only after all affected rows are evaluated. History-only records are never
reopened or deleted; maintenance changes listing metadata, not application states.

Cleanup reports add `candidate_rows` and `observation_updates`. The `fresh`,
`old`, `unknown_date`, `confirmed_closed`, `confirmed_stale`, and ambiguous counters
refer to the evaluated job candidates; on full migration they still cover all
jobs. `total_stored_listings` and `applications_preserved` remain whole-store
counts. These aggregate count queries still read SQLite's compact table/index
structure; this is not a claim of constant CPU cost for every statement.

### Statistics and read paths

Observation mutation triggers mark listing statistics dirty. Refresh is skipped
when the sidecar is valid, clean, and from the same UTC day. A dirty cleanup
recomputes once before the existing history flush, which incorporates those
listing statistics. If no application export is pending, the existing history
aggregate is updated once directly. Source discovery keeps its existing batching
and provenance behavior; unchanged cleanup does not recompute either aggregate.
The two discovery counters (sightings/duplicates versus unique listings) retain
their separate meanings.

Status reads the persisted listing-statistics snapshot and exposes its
`listing_statistics_as_of` and the periodic maintenance deadline. Queue and
pending display perform read-only freshness filtering on their returned rows;
manual holds and submission intents remain visible. The queue limit is applied
after filtering. Missing/corrupt statistics can be calculated for display without
writing files. Explicit refresh repairs the sidecar.

The CLI opts out of listing startup maintenance for status/queue/recent/pending.
The constructor still initializes schema and validates/flushes history: this is
an incremental reduction in display mutations, not the Phase 4 read-only database
constructor redesign.

Failed-attempt and closure paths synchronize the affected observation rather
than invoking unrelated global cleanup. They preserve existing application
transition/hold rules and do not clear controlled targets.

## 3. Query/index changes

Plans below were captured on both 100-row and 1,000-row synthetic datasets.
`after.json` retains the harness field name `plans_before`, meaning the plan on
the loaded implementation before any harness-created indexes; the harness adds
no candidate indexes. The production initialization supplies these indexes.

| Index and supported query | Before EQP | After EQP | Why needed |
| --- | --- | --- | --- |
| `jobs_canonical_url ON jobs(canonical_url)`; `identity_key=? OR canonical_url=?` | `SCAN jobs` | `MULTI-INDEX OR`; searches `sqlite_autoindex_jobs_1 (identity_key=?)` and `jobs_canonical_url (canonical_url=?)` | Existing unique identity index covers only one OR branch. URL index is deliberately nonunique. |
| `events_application ON events(application_id)`; `WHERE application_id=? ORDER BY id` | `SCAN events` | `SEARCH events USING INDEX events_application (application_id=?)` | SQLite's `id INTEGER PRIMARY KEY` is the rowid suffix already carried by the index, so a second explicit `id` column is redundant. No temporary sort. |
| `job_sources_job ON job_sources(job_id)`; `WHERE job_id=?` | `SCAN job_sources` | `SEARCH job_sources USING INDEX job_sources_job (job_id=?)` | Existing uniqueness is `(source_name, source_job_id)`, with a different leading key; that uniqueness remains intact. |

The only other index is `listing_maintenance_due(due_at)`, required by the scoped
maintenance implementation. `maintenance-plans.json` records indexed deadline,
job, observation, application, and source lookups; no full jobs/observations scan
is needed for ordinary candidate selection. No writing, priority, intent-count,
notification, or reporting indexes are added.

`measure_event_index.py` isolates insertion overhead using five in-memory runs
of 20,000 events distributed across 1,000 application IDs. Median insertion was
**10.181 ms without** and **16.749 ms with** the application index; database pages
occupied **1,101,824 versus 1,327,104 bytes**. These small synthetic samples show a
reasonable absolute insertion/storage tradeoff, not production write latency.
Raw samples and plans are in `event-index.json`.

## 4. Maintenance and safety boundaries

Persisted maintenance state is a scheduling/reporting optimization, never
permission to process a job. Claim still invokes `guard_listing`; application
attempt start and the final submission boundary still invoke the same live guard.
Final-submit code is unchanged. Manual-resume/retry guards remain in place.
Unknown/invalid/non-posting evidence stays unknown; future dates remain ineligible
until valid under the existing policy. Exact cutoff behavior and the 30-day
maximum remain authoritative in `freshness.py`.

Tests preserve submitted records, durable submission intents, manual holds,
retirement guards, controlled targets, events, confirmation data, and status
history. Cached ACTIVE state is explicitly tested against changed evidence both
at claim and between claim and attempt start. Existing local-browser tests cover
stale/closed/unknown changes immediately before final submission and assert zero
submission interactions for those attempts.

SQLite remains WAL. There are no transactions across browser/network awaits.
History export remains synchronous under the existing DB/history lock protocol;
no asynchronous exporting, lock removal, or revision/ack redesign is included.
The existing filesystem work under the history lock is intentionally retained.

## 7. Remaining issues for later phases

History initialization/export and history statistics still perform synchronous
filesystem work under their existing locks. Listing statistics still scan all
observations when genuinely dirty or on a UTC-day rollover; this phase avoids
redundant recomputation rather than redesigning aggregate storage. Status exposes
a persisted statistics snapshot, while processing always uses live freshness.
The broader read-only constructor, revisioned/deferred history export, profile
snapshots, browser caching, preflight, and lifecycle/adapter work remain deferred.
No Phase 4 work is started.
